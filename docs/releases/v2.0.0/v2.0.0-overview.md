# Trackora v2.0.0 — Phase 0 Overview

**Version:** 2.0.0-draft  
**Status:** Planning / Phase 0  
**Theme:** Platform Modernization + User Experience Refinement + Upgrade Foundation  
**Document Type:** Release Overview  
**Owner:** Architecture Team  

---

## Purpose

Define the architectural scope, milestone structure, dependency topology, risk register, testing strategy, and implementation sequencing for Trackora v2.0.0. This document is the single source of truth for the v2.0.0 release plan and serves as the entry point for all downstream milestone documents.

---

## Scope

### In Scope

| Milestone | Description |
|-----------|-------------|
| M8 — Upgrade Foundation | SchemaVersionManager, MigrationManager, BackupManager; user data survival guarantee across all future upgrades |
| M9 — MongoDB Foundation | Replace Supabase reporting backend with MongoDB; MongoReportService; MongoDB Schema V1 for reports, feedback, feature_requests |
| M10 — Update Center | GitHub release detection; update banner; tray notification; release notes display; notification-only updater |
| M11 — Automatic Game Discovery | Auto-detection for Steam, Epic Games, Riot, Battle.net, Ubisoft Connect, Xbox/Game Pass, Windows installed applications, common game folders; manual EXE fallback |

### Out of Scope

- MongoDB Schema V2+ (deferred to v2.1+)
- MongoDB local storage of game/session data (SQLite remains system of record)
- Automatic update download and installation (notification-only in v2.0)
- Game library import/export
- Cloud sync of user data
- Multi-user or role-based access

## Architectural Risks

| ID | Risk | Impact | Likelihood | Mitigation |
|----|------|--------|------------|------------|
| AR-01 | Upgrade Foundation introduces schema coupling that makes future migrations brittle | Medium | Low | Contract-first design; every migration must be idempotent, tested, and versioned |
| AR-02 | MongoDB dependency conflicts with PyInstaller frozen build | High | Medium | Test PyInstaller build with MongoDB driver early; verify hidden imports and DLL bundling |
| AR-03 | Game discovery heuristics produce false positives (non-game executables) | Medium | Medium | Whitelist-based detection with user confirmation; allow manual override |
| AR-04 | Game discovery misses platform installations due to registry/permission changes | Medium | Medium | Defensive detection with graceful fallback; log all detection failures for diagnostics |
| AR-05 | Update Center polls GitHub and triggers rate limiting | Low | Medium | Cache release check results; respect GitHub ETag/rate-limit headers; configurable poll interval |
| AR-06 | MongoDB ReportService introduces network dependency in a local-first application | Medium | Low | Treat all MongoDB submissions as best-effort; offline queue must remain functional; AbstractReportService contract unchanged |
| AR-07 | User data loss during migration if BackupManager fails | Critical | Low | Atomic backup before migration; verify checksum after backup; fail-safe rollback; tested recovery |
| AR-08 | Multiple Trackora versions share the same APPDATA directory with incompatible schemas | High | Low | SchemaVersionManager prevents execution on unsupported schema versions; clear error message |

## Migration Risks

| ID | Risk | Impact | Mitigation |
|----|------|--------|------------|
| MR-01 | Existing SQLite schema must evolve for v2.0 features | Medium | Each migration is a single atomic transaction; rollback on failure; backup before applying |
| MR-02 | User data from v1.1.x must be forward-compatible with v2.0.0 | Critical | Validate all v1.1.x data structures against v2.0.0 schema before migration; block upgrade on incompatibility |
| MR-03 | MongoDB Schema V1 must be created without conflicting with SQLite schema | Low | Separate data domains; SQLite for local tracking, MongoDB for opt-in reporting |
| MR-04 | MigrationManager must survive partial migration (crash during migration) | High | All migrations are idempotent; MigrationManager records applied migrations atomically; recovery re-applies on restart |
| MR-05 | Downgrade from v2.0.0 to v1.1.x is unsupported | Medium | Document that upgrades are one-way; BackupManager provides data export for manual restore |
| MR-06 | Schema version metadata must survive application reinstall | High | Store schema version in APPDATA (user data), not in Program Files (app data) |

## Testing Requirements

### Architecture Enforcement Tests (new)

| Area | Requirement | Milestone |
|------|-------------|-----------|
| SchemaVersionManager isolation | Only SchemaVersionManager may read/write schema version metadata | M8 |
| MigrationManager isolation | Only MigrationManager may apply schema migrations | M8 |
| BackupManager isolation | Only BackupManager may create/restore backups | M8 |
| MongoDB path isolation | MongoDB connection strings/config must not appear in UI layer | M9 |
| Update Center path isolation | GitHub release cache must use paths.py | M10 |
| Game discovery isolation | Game platform detection must not contain UI imports | M11 |

## Recommended Implementation Order

### Phase 0 (Current) — Documentation & Planning

```
 1. Architecture validation (this document set)
 2. Risk acceptance
 3. Dependency graph review
 4. Phase 0 Completion Checklist sign-off
```

### Phase 1 — Foundation (M8)

```
 1. SchemaVersionManager
 2. BackupManager
 3. MigrationManager
 4. Migration: v1.1.x → v1.2.0 schema (if needed)
 5. Architecture enforcement tests
 6. Unit tests (all M8 test files)
 7. Integration tests (full migration lifecycle)
```

### Phase 2 — Milestones (M9, M10, M11) — Parallel

```
 Track A — M9 MongoDB Foundation:
   1. MongoDB connection manager (trackora.core)
   2. MongoReportService (services/support/)
   3. MongoDB Schema V1 (reports, feedback, feature_requests)
   4. Schema version enforcement in every document
   5. Unit + integration tests
   6. Architecture enforcement tests
   7. SupportService DI wiring update

 Track B — M10 Update Center:
   1. GitHubReleaseChecker (services/)
   2. UpdateCenterService (services/)
   3. Cache layer (paths.py extension)
   4. UI: update banner (main_window)
   5. UI: tray notification (tray_service)
   6. UI: release notes dialog
   7. Unit + integration tests

 Track C — M11 Game Discovery:
   1. GameDetectorProtocol / interface
   2. SteamDetector
   3. EpicDetector
   4. RiotDetector
   5. BattleNetDetector
   6. UbisoftDetector
   7. XboxDetector
   8. WindowsAppDetector
   9. CommonFoldersDetector
  10. ManualExeDetector
  11. GameDiscoveryOrchestrator
  12. Integration with existing GameService
  13. Unit + integration tests for each detector
```

### Phase 3 — Integration & Validation

```

 2. PyInstaller build verification (MongoDB driver compatibility)
 3. Inno Setup installer verification
 4. Upgrade path test: v1.1.x → v2.0.0
 5. Performance benchmark comparison
 6. Architecture enforcement sweep
```

```
 1. CHANGELOG update
 2. version_info.txt update (1.1.0.0 → 2.0.0.0)
 3. CI/CD pipeline update
 4. Release notes generation
 5. Tag and release
```

## Future Extensibility Notes

### v3.0 Considerations

- MongoDB Schema V2 may add sessions, games, and settings collections for cloud sync
- Full automatic update download and installation
- Game discovery may extend to GOG, itch.io, Amazon Games
- MigrationManager must support multi-step version chaining (v1.x → v2.x → v3.x)

### v4.0+ Considerations

- MigrationManager must support parallel migration tracks (SQLite and MongoDB)
- SchemaVersionManager must support multiple database backends
- BackupManager may support cloud backup targets
- Game discovery may support Linux (Steam Proton, Lutris) and macOS
